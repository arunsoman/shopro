# Flow Extractor Skill

Scan every `.tsx` file in a project, extract **every user-facing workflow** (no
matter how small), and write structured entries to `docs/flow.md`.

---

## What counts as a flow?

Capture **everything** a user can trigger or experience, including:

| Category | Examples |
|---|---|
| Navigation | Clicking a link, tab, breadcrumb, back button |
| Forms | Filling, submitting, resetting, validating a form |
| Auth | Login, logout, register, forgot password, OTP |
| Data ops | Search, filter, sort, paginate, refresh |
| Modals / Sheets | Opening, closing, confirming, cancelling |
| CRUD | Create, read, update, delete any entity |
| Feedback | Toasts, alerts, error states, empty states, loading |
| Commerce | Add to cart, checkout, payment, order tracking |
| Role-gated | Any flow that only certain roles can access |
| Micro-interactions | Toggle, like, bookmark, copy, share |
| Onboarding | First-run tours, setup wizards, welcome screens |

## Step-by-step execution

### 1. Discover all TSX files

```bash
find <PROJECT_ROOT> -name "*.tsx" \
  ! -path "*/node_modules/*" \
  ! -path "*/.next/*" \
  ! -path "*/dist/*" \
  ! -path "*/__tests__/*" \
  ! -path "*.test.tsx" \
  ! -path "*.spec.tsx" \
  | sort
```

Store the list. Process files **one at a time** in order.

### 2. For each file — analyse and extract flows

Read the file fully. Look for all of the following signals:

**UI signals (JSX)**
- `<Button>`, `<Link>`, `onClick`, `onSubmit`, `onChange`, `onSelect`
- `<form>`, `<input>`, `<select>`, `<textarea>`
- `<Dialog>`, `<Modal>`, `<Sheet>`, `<Drawer>`, `<AlertDialog>`
- `<Tabs>`, `<Accordion>`, `<Popover>`, `<DropdownMenu>`
- `<Table>`, `<DataTable>`, pagination components
- `<Toast>`, `<Alert>`, `<Badge>`, `<Skeleton>` (loading)
- `router.push`, `router.replace`, `navigate`, `redirect`

**Logic signals (TypeScript)**
- `useState`, `useReducer` — what state is toggled/updated?
- `useEffect` — what side-effects happen on mount or dependency change?
- `useMutation`, `useQuery` — what data operations are performed?
- `fetch`, `axios`, `trpc` calls — what endpoints are hit?
- Conditional rendering based on `role`, `isAuthenticated`, `permissions`
- `try/catch` blocks — what error paths exist?

**Role signals**
- Variables / props named `role`, `userType`, `isAdmin`, `isSeller`,
  `isBuyer`, `isVendor`, `isGuest`, etc.
- Conditional rendering: `{user.role === 'admin' && ...}`
- Route guards, middleware references

### 3. Infer the screen name

Use this priority order:
1. The component's display name or `export default function <Name>`
2. The file path (e.g. `app/seller/products/page.tsx` → "Seller Products Page")
3. The `<title>` or heading text rendered in JSX

### 4. Infer the user role

Default roles for a marketplace (adjust to what you see in code):

| Code hint | Role label |
|---|---|
| `isBuyer`, `buyer`, `customer` | Buyer |
| `isSeller`, `seller`, `vendor` | Seller |
| `isAdmin`, `admin` | Admin |
| No role guard, public route | Guest / Any User |
| `isAuthenticated` only | Authenticated User |

### 5. Write each flow entry

Every distinct interaction = one entry. Be **generous** — log even tiny flows
like "user closes a modal" or "user copies a link".

## Output format — docs/flow.md

### File header

```markdown
# Shopro Marketplace — User Flow Documentation

> Auto-generated by the Flow Extractor skill.  
> Last updated: <ISO date>  
> Source: <PROJECT_ROOT>

---
```

### Per-file section

```markdown
## <Screen Name>

**File:** `<relative/path/to/file.tsx>`

---

### Flow: <Short Flow Name>

| Field | Value |
|---|---|
| **Screen** | <Screen Name> |
| **Flow Name** | <Short Flow Name> |
| **User Role** | <Role> |
| **Trigger** | <What the user does to start this flow> |

**Description:**  
<2–5 sentence detailed description. Explain: what the user sees, what they
interact with, what happens next (API call? navigation? state change? feedback
message?), and any edge cases or error paths visible in the code.>

---
```

Repeat a `### Flow:` block for **every** flow found in the file.

After the last flow for a file, add a horizontal rule before the next `##` section.

### File footer

```markdown
---

*Total flows documented: <N>*
```

## Quality rules

- **Never skip a file.** Even a file with only one button gets a flow entry.
- **Never merge two distinct interactions** into one flow entry.
- **Err on the side of more entries**, not fewer.
- If a component is used in multiple roles (e.g. a shared `ProductCard`), log a
  flow for each role that could realistically use it.
- If a flow has an error/empty state, document it as a **separate flow** entry
  (e.g. "User views empty cart" vs "User views cart with items").
- Do **not** document internal developer utilities, test harnesses, or Storybook
  stories.
